## 2. Tres bugs reales encontrados y corregidos

Los tres habrían roto el 100% de las 58 herramientas del catálogo en producción:

1. **Modelo de licencia inexistente.** `guarda_llave.py` referenciaba `x_booster_licencia`, que no existía en ningún tenant. Se creó en Odoo: modelo (`ir.model` id 2707), campos `x_fecha_renovacion` (datetime) y `x_tenant` (char), regla de acceso, y un registro inicial. Documentado ahora en `01-booster-implementador.md`: el modelo debe crearlo Booster durante el provisioning, nunca asumirlo preexistente.

2. **`datetime.now()` no funciona en el sandbox de Odoo.** `datetime` llega como `wrap_module`, no como el módulo real — `datetime.now()` lanza `'wrap_module' object has no attribute 'now'`. Hay que usar `datetime.datetime.now()`. Corregido en `guarda_llave.py`, documentado con el error exacto.

3. **Odoo no acepta JSON Schema completo en `ai_tool_schema`.** Se probó campo por campo creando/borrando Server Actions temporales:
   - **Acepta:** `type`, `description`, `enum`, `pattern` por propiedad; `array` con `items` escalar; a nivel raíz `type:"object"` + `properties` + `required` (este último obligatorio, aunque vaya vacío).
   - **Rechaza:** `default`, `minLength`, `maxLength`, `format`, `minimum`, `maximum`, `exclusiveMinimum`, `minItems`, `maxItems`, objetos anidados, arrays de objetos, `$ref`/`$defs`, `anyOf`/`oneOf`.

   El catálogo (`herramientas_esquemas.json`) sigue en JSON Schema completo (es la spec de negocio). Se construyó `server_actions/esquemas_odoo.py` como capa de traducción: resuelve `$ref`, aplana objetos anidados (`periodo` → `periodo_desde`/`periodo_hasta`), convierte arrays de objetos en un parámetro string `<nombre>_json`, y traslada a la descripción las restricciones que Odoo descarta (para que el modelo las siga "viendo" aunque ya no se validen). Verificado con 12 tests (`test_esquemas_odoo.py`), incluyendo uno que carga el catálogo real completo y confirma que las 58 herramientas traducen sin error. Además, se instalaron en vivo (y se borraron) los 6 casos más difíciles del catálogo (`crear_cotizacion`, `registrar_conteo`, `nota_vendedor`, `crear_campana_borrador`, `alerta_vencimiento`, `cierre_mensual`) para confirmar que Odoo los acepta de verdad, no sólo en el test.

## 3. Primera herramienta con lógica real, probada en producción

`server_actions/implementaciones/ventas_atencion/crear_actualizar_lead.py` — antes sólo existían esqueletos con `TODO`. Ahora hay una regla explícita en `implementaciones/README.md`: una herramienta sólo cuenta como "implementada" cuando fue probada en vivo con llave vigente (camino feliz) **y** con llave vencida (kill-switch). El estado actual es 1 de 58.

Lógica de esta herramienta: valida nombre + interés (obligatorios), valida teléfono-o-email (a mano, porque `anyOf` no lo soporta el esquema saneado), busca lead existente por email y luego por teléfono, actualiza (acumula el interés en la descripción) o crea, siempre respetando permisos reales del usuario (sin `sudo()`, salvo la guarda).

## 7. Convenciones que hay que seguir escribiendo herramientas nuevas

- La guarda de licencia va **siempre primero** en el `code` de cada Server Action (`GUARDA_TEMPLATE` de `guarda_llave.py`).
- `datetime.datetime.now()`, nunca `datetime.now()`.
- Nunca `sudo()` fuera de la guarda — la herramienta corre con los permisos reales del usuario que habla con el agente.
- Las variables que recibe el código son las del esquema **saneado** (`esquemas_odoo.py`), no las del catálogo — ej. `periodo_desde`/`periodo_hasta`, no `periodo`; `lineas_json`, no `lineas`.
- Toda validación que el esquema ya no impone (`anyOf`, mínimos, formatos) se valida a mano en el cuerpo de la Server Action.
- Conventional Commits; push a `main` requiere confirmación explícita de Alberto.
